3. 系统功能说明

3.1 用户注册功能

现有用户注册功能满足：

  • 用户名只允许包含字母、数字和下划线；
  • 用户名长度限制为 4 至 20 位；
  • 用户名在数据库中唯一，重复注册会被拒绝；
  • 密码长度至少为 6 位；
  • 密码必须同时包含字母和数字；
  • 密码在数据库中以哈希值保存，不以明文形式存储。

后端注册接口由 AuthController.java 和 AuthService.java 实现。前端注册页面位于 RegisterPage.tsx，页面在用户输入阶段就会给出实时提示，从而减少无效请求。

下面两张图展示注册功能的页面表现：

注册功能不仅实现了“能写入数据库”，还实现了字段约束、唯一性校验和错误提示闭环。

3.2 用户登录功能

本项目的处理方式如下：

  • 账号密码正确时，登录成功并进入任务管理界面；
  • 账号密码错误时，返回明确提示“用户名或密码错误”；
  • 未登录用户访问受保护任务接口时，会被后端拦截并返回 401；
  • 本地已保存但失效的 Token 会在前端自动清理，并跳转回登录页；
  • 页面刷新后，前端会读取本地登录态并继续访问当前用户任务。

登录页位于 LoginPage.tsx，登录态维护逻辑位于 AuthContext.tsx、storage.ts 和 http.ts。后端鉴权链路则由 SecurityConfig.java、JwtAuthenticationFilter.java 和 JwtService.java 实现。

3.3 个人任务管理功能

登录后的用户可以在任务页中管理自己的个人任务。系统目前支持：

  • 创建任务
  • 查看任务列表
  • 查看任务详情
  • 修改任务
  • 删除任务
  • 对任务列表进行分页、状态筛选、优先级筛选，以及前端关键词过滤

每个任务包含以下字段：

  • 标题 title
  • 描述 description
  • 状态 status
  • 优先级 priority
  • 截止时间 dueAt
  • 创建时间 createdAt
  • 更新时间 updatedAt

这些字段在实体类 Task.java 中定义，并通过 AuditableEntity.java 统一补充创建时间与更新时间。

任务页面位于 DashboardPage.tsx，后端任务接口位于 TaskController.java 和 TaskService.java。

3.4 用户数据隔离

Lab1 明确要求“用户只能查看和操作自己的任务”。本项目通过以下方式实现：

  • 任务表中通过 owner_id 与用户表关联；
  • 后端每次操作任务时，先根据当前登录用户查询对应 User；
  • 查询、更新、删除任务时，都会同时校验 taskId 和 ownerId；
  • 如果任务不存在，或者不属于当前用户，统一返回“任务不存在，或你无权访问该任务”。

也就是说，用户 A 无法通过构造请求直接读取或删除用户 B 的任务。这一点既在服务层逻辑中实现，也在集成测试中验证通过。

4. 系统设计与实现质量说明

4.1 前后端分离架构

本项目采用前后端分离架构：

  • 前端负责页面展示、表单交互、状态维护和错误提示；
  • 后端负责身份认证、业务逻辑、数据库操作和接口返回；
  • 前后端通过 REST 风格接口通信，统一使用 JSON 交换数据。

目录结构上，后端位于 backend/，前端位于 frontend/，两者可独立启动、独立构建、独立测试。

4.2 数据库设计

本项目目前主要包含两张核心表：

  1. users
  2. tasks

其中：

  • users 表保存用户 ID、用户名、密码哈希和审计字段；
  • tasks 表保存任务基础信息，并通过 owner_id 关联所属用户；
  • 状态、优先级、排序类型等使用枚举实现，避免使用魔法字符串或魔法数字；
  • title、description、username、password_hash 等字段都设置了长度与非空约束。

以实体设计为例：

  • User.java 中，用户名设置为唯一且长度不超过 20；
  • Task.java 中，任务标题、描述、状态、优先级、截止时间与所属用户关系都进行了清晰建模。

这种设计既满足 Lab1 的字段需求，也为后续增加团队、成员、评论、依赖关系等扩展留下了空间。

4.3 异常处理设计

为了避免接口返回风格混乱，本项目实现了统一异常处理机制：

  • 业务校验错误使用 BusinessException
  • 资源不存在或越权访问使用 ResourceNotFoundException
  • 参数校验错误通过 MethodArgumentNotValidException 统一转换
  • 兜底异常统一返回“服务器内部错误，请稍后重试”

统一处理逻辑位于 GlobalExceptionHandler.java。所有接口统一返回 ApiResponse 结构，这样前后端在处理正常响应和错误响应时都更稳定，避免“同一种错误在不同接口里格式不一致”的情况。

4.4 代码结构清晰与可扩展性

为了方便后续 Lab 继续扩展，本项目在结构上尽量避免把逻辑堆进一个控制器或一个服务类中，而是采用模块化拆分：

  • auth 模块：注册、登录、JWT、用户认证
  • task 模块：任务实体、DTO、服务、控制器、算法
  • user 模块：用户实体、仓库、查询服务
  • common 模块：统一返回结构、异常、审计基类
  • config 模块：安全配置、JWT 配置

前端同样进行了拆分：

  • pages 放页面级组件
  • components 放可复用组件
  • api 放请求封装
  • context 放全局登录态
  • types 放类型定义
  • utils 放工具函数

这种结构使当前 Lab1 的代码已经具备“继续迭代”的条件。

5. 关键设计说明

5.1 选择 JWT 而不是 Session

我们最终选择 JWT的主要原因：

  1. 前后端分离项目中，JWT 更适合前端通过请求头携带身份信息；
  2. 页面刷新后可以通过本地保存的 Token 继续维持登录态；
  3. 后续若扩展多人协作、移动端或更多前端页面时，JWT 方案更容易统一。

5.2 任务状态和优先级使用枚举

我们使用：

  • TaskStatus
  • TaskPriority
  • SortBy
  • TaskUrgencyLevel

这些枚举统一表达业务语义。

5.3 任务列表加入分页和筛选

我们做了两层考虑：

  1. 接口层支持分页，避免任务数量增大后一次性返回全部数据；
  2. 页面层支持状态、优先级筛选，并额外提供前端关键词过滤，提高任务管理效率。

这样既能满足当前 Lab1 的最小版本需求，也能体现我们对后续扩展的预判。

二、git日志与ai说明

7. Git 协作与分支流程说明

我们在开发过程中采用了 main / develop / feature / hotfix 的分支结构，并尽量按照 GitFlow 的要求开展开发。整体流程如下：

  1. 以 main 作为主分支；
  2. 从 main 拉出 develop 作为日常集成分支；
  3. 新功能从 develop 创建 feature/* 分支；
  4. 功能完成后通过 Merge Request 合并回 develop；
  5. 当里程碑稳定后，再将 develop 合并到 main；
  6. 发现主干问题后，再通过 hotfix/* 分支修复。

从仓库历史看，我们并不是只建立了一个或两个临时分支，而是确实围绕不同模块使用了较完整的 feature/* 与 hotfix/* 流程。为了更贴近评分点，这里将分支使用情况进一步拆开说明。
